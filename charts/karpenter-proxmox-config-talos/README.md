# karpenter-proxmox-config-talos

Helm chart that generates the Cloud-Init configuration and (optionally) the Karpenter Custom Resources required to scale a Talos cluster on Proxmox using [karpenter-provider-proxmox](https://github.com/sergelogvinov/karpenter-provider-proxmox).

This chart does not install Karpenter itself, and does not build the Proxmox VM template. It only generates:

1. A **Cloud-Init template** Secret (the `user-data` / `network-config` Go templates rendered at provisioning time)
2. A **Cloud-Init values** Secret (the variables injected into the template above)
3. Optionally, the **ProxmoxNodeClass**, **NodePool**, and **ProxmoxUnmanagedTemplate** / **ProxmoxTemplate** custom resources

---

## How the pieces fit together

```
ProxmoxNodeClass.metadataOptions.templatesRef  ──▶  karpenter-talos-cloudinit-template (Secret)
ProxmoxNodeClass.metadataOptions.valuesRef     ──▶  karpenter-talos-cloudinit-values   (Secret)
ProxmoxNodeClass.spec.instanceTemplateRef      ──▶  ProxmoxUnmanagedTemplate / ProxmoxTemplate
NodePool.nodeClassRef                          ──▶  ProxmoxNodeClass
```

When Karpenter provisions a new node, it clones the referenced Proxmox VM template, builds a Cloud-Init ISO from the template Secret rendered with the values Secret, and attaches it to the VM as a CD-ROM. The VM's `cloud-init` then configures the OS and joins the node to the Talos cluster as a worker.

---

## 1. The VM template

The chart does **not** build the Proxmox VM template — that is a one-time, out-of-band step. The template must be built from the [Talos Proxmox image](https://www.talos.dev/latest/talos-guides/install/virtualized-platforms/proxmox/) (the `nocloud` variant, since Karpenter delivers Cloud-Init as an ISO), with:

- `boot: order=scsi0` rather than the legacy `boot: c` format — this is the format Karpenter writes when attaching the Cloud-Init CD-ROM, and a template still using the legacy `boot: c` format will fail with `boot.legacy: value does not match the regex pattern`. Both SeaBIOS and OVMF work fine with `boot: order=scsi0`; only the boot-order syntax matters here, not the BIOS type.
- **No Proxmox Cloud-Init drive** (`scsi1: <storage>:cloudinit`) needed — the `network-config` generated by Karpenter's own Cloud-Init ISO configures DHCP over IPv4 on the detected interface, which is enough for these nodes.
- `qemu-guest-agent` can be built into the official Talos image — use the appropriate image ID from the [Talos Factory](https://factory.talos.dev/) when generating/downloading the image, so it reports the VM's IP/state to Proxmox without any further customization.

Unlike a generic Linux distribution, there is no "pre-install vs install-at-boot" choice to make here: Talos itself ships baked into the template image, and the Cloud-Init `user-data` only supplies the **machine config** (the equivalent of `worker.yaml`) that Talos consumes on first boot to join the cluster. There is no package installation step at provisioning time, and therefore no outbound internet dependency at node boot.

### Resetting a manually-installed Talos VM before converting it to a template

If the VM was installed manually from an ISO (rather than generated as a ready-to-clone disk image), it must be reset before conversion — otherwise the clone inherits node-specific state (`STATE` and `EPHEMERAL` partitions) from that installation, the same class of problem as a stale `/etc/machine-id` on a generic Linux template:

```bash
talosctl reset --system-labels-to-wipe STATE --system-labels-to-wipe EPHEMERAL -n $WORKER_IP
```

This is a **soft reset**: it wipes the `STATE` and `EPHEMERAL` partitions (cluster identity, runtime state) while leaving the underlying disk and installed Talos version intact, so the VM remains bootable as a clean template. Only convert the VM to a Proxmox template *after* this reset completes and the VM has shut down.

## 2. Cloud-Init template (`cloudInitTemplate`)

Rendered into a Secret named `cloudInitTemplate.name` (default `karpenter-talos-cloudinit-template`), referenced by `ProxmoxNodeClass.spec.metadataOptions.templatesRef`.

### Values

| Key | Description |
|---|---|
| `cloudInitTemplate.name` | Name of the generated Secret. |
| `cloudInitTemplate.kubeletVersion` | Version of the Kubelet to install on the node (e.g. `v1.36.0`). |
| `cloudInitTemplate.installWipe` | `true`/`false` — whether the installation disk should be wiped at install time. See **Disk wipe** below. Default `true`. |
| `cloudInitTemplate.disableDefaultCni` | `true`/`false` — disables Talos' default CNI (Flannel) so it can be replaced by another CNI (Calico, Cilium, …). Adds `cluster.network.cni.name: none` to the machine config. Default `false`. |
| `cloudInitTemplate.proxyDisabled` | `true`/`false` — disables kube-proxy, typically when the CNI replaces it. **Must match the CNI's own expectation** (for Cilium, this must match the `kubeProxyReplacement` Helm value used for the CNI itself — an inconsistency here leaves the cluster with neither kube-proxy nor a working replacement). Default `false`. |

### What the rendered `user-data` contains

- A Talos worker machine config (the Cloud-Init equivalent of `worker.yaml`), built from the cluster identity values below (`machineToken`, `machineCA`, `clusterID`, `clusterSecret`, `clusterEndpoint`, `clusterName`)
- The Kubelet version pin (`kubeletVersion`)
- The disk-wipe directive controlling whether `install.wipe` is set for the target installation disk
- Optionally, `cluster.network.cni.name: none` and the kube-proxy `disabled` flag, when a non-default CNI is used

> **Note on `provider-id`:** unlike installers that require you to manually wire a kubelet `--provider-id` flag, Talos derives the node's provider ID itself from the underlying platform metadata once the VM boots under the `nocloud` platform. There is nothing to template manually here — just make sure the template was built for the `nocloud` platform and not bare-metal/ISO.

### Disk wipe (`installWipe`)

**Why this exists:** if the Proxmox VM template's disk already contains a previous Talos installation (e.g. it was booted once during the template-build process, or cloned from a VM that already ran Talos), the installer will refuse to overwrite an existing installation unless explicitly told to wipe it first. Without wiping, the clone can fail to install or — worse — boot into a stale, half-configured system from whatever state the template happened to be in.

Set `installWipe: true` (the default) unless you have independently verified that every clone of your VM template starts from a disk that has never had Talos installed on it (e.g. the template was built directly from the official Talos disk image and never booted). If in doubt, leave it `true` — a wipe of an already-empty disk is a no-op and harmless.

## 3. Cloud-Init values (`cloudInitValues`)

Rendered into a Secret named `cloudInitValues.name` (default `karpenter-talos-cloudinit-values`), referenced by `ProxmoxNodeClass.spec.metadataOptions.valuesRef`. These are the variables substituted into the template Secret above (`.Values.*` in the Go template).

| Key | Description |
|---|---|
| `cloudInitValues.name` | Name of the generated Secret. |
| `cloudInitValues.machineToken` | Talos' `machine.token` (found in `worker.yaml`) — equivalently `trustdinfo.token` in `secrets.yaml`. Treat as a secret — avoid committing it in plaintext to version control. |
| `cloudInitValues.machineCA` | Talos' `machine.ca.crt` (found in `worker.yaml`) — equivalently `certs.os.cert` in `secrets.yaml`. |
| `cloudInitValues.clusterID` | Talos' `cluster.id` (found in both `worker.yaml` and `secrets.yaml` — must match across the cluster). |
| `cloudInitValues.clusterSecret` | Talos' `cluster.secret` (found in both `worker.yaml` and `secrets.yaml`). Treat as a secret. |
| `cloudInitValues.clusterEndpoint` | URL of the existing Talos control-plane endpoint, e.g. `https://master.example.local:6443`. Talos' `cluster.controlPlane.endpoint` (found in both `worker.yaml` and `controlplane.yaml`). |
| `cloudInitValues.clusterName` | Talos' `cluster.clusterName` (found in both `worker.yaml` and `controlplane.yaml`). |

> **Where to find these values:** all of them already exist in your cluster's generated configuration — there is nothing to invent. If you have `worker.yaml` from `talosctl gen config`, every field above except `clusterID`/`clusterSecret` is read straight from it; the two remaining fields come from `secrets.yaml` generated at the same time. If you no longer have these files, they can also be recovered from a running control-plane node (`talosctl get machineconfig` / the secrets bundle), but regenerating `secrets.yaml` from scratch is **not** an option — every worker and control-plane node must share the exact same cluster secret material, so existing nodes would otherwise be left orphaned from any newly provisioned one.

> **Note on node naming:** Talos derives the Kubernetes `Node` name from the VM's hostname as reported via Cloud-Init/DHCP, consistently with how Karpenter expects to match a `NodeClaim` to its resulting `Node`.

## 4. Karpenter Custom Resources (optional)

The chart can optionally create the `ProxmoxNodeClass`, `NodePool`, and `ProxmoxUnmanagedTemplate`/`ProxmoxTemplate` resources, so the whole node pool can be deployed as a single Helm release.

### `nodeTemplate`

One entry per VM template you want Karpenter to be aware of.

| Key | Description |
|---|---|
| `nodeTemplate.<name>.enabled` | Create this `ProxmoxUnmanagedTemplate`/`ProxmoxTemplate` resource. |
| `nodeTemplate.<name>.kind` | `ProxmoxUnmanagedTemplate` (template not managed by Karpenter, e.g. built by an external script as described above) or `ProxmoxTemplate` (Karpenter manages the template lifecycle itself). |
| `nodeTemplate.<name>.spec` | Raw spec, e.g. `templateName: <proxmox-template-name>`. See the [nodetemplateclass reference](https://github.com/sergelogvinov/karpenter-provider-proxmox/blob/main/docs/nodetemplateclass.md). |
| `nodeTemplate.<name>.tags` | (Optional) Match the template by Proxmox tags instead of/in addition to name. |

### `nodeClass`

One entry per `ProxmoxNodeClass`. Ties together the VM template, the boot disk sizing, and the two Cloud-Init Secrets above.

| Key | Description |
|---|---|
| `nodeClass.<name>.enabled` | Create this `ProxmoxNodeClass`. |
| `nodeClass.<name>.spec.instanceTemplateRef` | Points at the `nodeTemplate` entry above. |
| `nodeClass.<name>.spec.bootDevice` | Root disk size and Proxmox storage. |
| `nodeClass.<name>.spec.metadataOptions` | Wires up `templatesRef`/`valuesRef` to the two Secrets generated by this chart, and sets `type: cdrom` so Cloud-Init is delivered as an ISO. |
| `nodeClass.<name>.spec.tags` | (Optional) Tags applied to provisioned VMs in the Proxmox UI, for visibility. |

See the [nodeclass reference](https://github.com/sergelogvinov/karpenter-provider-proxmox/blob/main/docs/nodeclass.md) for the full spec.

### `nodePools`

One entry per Karpenter `NodePool`. Standard Karpenter NodePool spec — see [karpenter.sh/docs/concepts/nodepools](https://karpenter.sh/docs/concepts/nodepools). `limits` caps the aggregate CPU/memory this pool is allowed to provision; `requirements` constrain instance selection (architecture, instance type, capacity type, etc.).

## Troubleshooting checklist

If a node is created in Proxmox but never reaches `Ready` in Kubernetes, work through these in order:

1. **`NodeClaim` stuck at `Ready: Unknown`, event `Nodeclaim does not have an associated node`**
   Check `kubectl get node <name> -o jsonpath='{.spec.providerID}'`. It must exactly match the NodeClaim's `Provider Id` (`proxmox://<region>/<vmid>`). Since Talos derives the provider ID itself from platform metadata under `nocloud`, a mismatch here usually points to the template not having been built for the `nocloud` platform, or to a stale/cached image used for the clone.

2. **Node never appears in `kubectl get nodes` at all**
   Use `talosctl` against the new node's IP (`talosctl -n <node-ip> dmesg` / `talosctl -n <node-ip> get machineconfig`) to confirm Talos actually received and applied the machine config delivered via Cloud-Init. An empty or default machine config means the Cloud-Init ISO wasn't attached correctly, or the `metadataOptions.type: cdrom` setting is missing from the `ProxmoxNodeClass`.

3. **`talosctl` shows a certificate/trust error joining the control plane**
   Double-check that `machineToken`, `machineCA`, `clusterID`, and `clusterSecret` were copied from the **same** `secrets.yaml`/`worker.yaml` pair as the existing control-plane nodes. Any mismatch between these four values and what the control plane expects will reject the join at the TLS/trust level rather than at the Kubernetes API level.

4. **Install fails or the node boots into a stale configuration**
   The target disk likely already contained a previous Talos installation that wasn't wiped. Confirm `installWipe: true`, or rebuild the VM template from a pristine, never-booted Talos disk image.

5. **CNI pods never reach `Running`, or kube-proxy and the CNI fight over the same ports**
   Check that `disableDefaultCni` and `proxyDisabled` are consistent with what the actual CNI Helm chart expects (e.g. Cilium's `kubeProxyReplacement` value). Setting `proxyDisabled: true` while the CNI is not actually configured to replace kube-proxy leaves the cluster without any kube-proxy-equivalent routing.

6. **`failed to attach cloud-init ISO ...: boot.legacy: value does not match the regex pattern`**
   The VM template uses legacy boot-order syntax `boot: c` instead of `boot: order=scsi0`.

7. **`NodeClaim` is destroyed after ~15 minutes while you're mid-debug**
   This is Karpenter's `registration_timeout` — expected behavior in production, inconvenient while iterating. Scale Karpenter to zero replicas while debugging (`kubectl scale deploy -n kube-system <karpenter-deployment> --replicas=0`), or test against a manually cloned VM outside of Karpenter's lifecycle entirely.
