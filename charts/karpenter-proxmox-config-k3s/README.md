# karpenter-proxmox-config-k3s

Helm chart that generates the Cloud-Init configuration and (optionally) the Karpenter Custom Resources required to scale a K3s cluster on Proxmox using [karpenter-provider-proxmox](https://github.com/sergelogvinov/karpenter-provider-proxmox).

This chart does not install Karpenter itself, and does not build the Proxmox VM template. It only generates:

1. A **Cloud-Init template** Secret (the `user-data` / `network-config` Go templates rendered at provisioning time)
2. A **Cloud-Init values** Secret (the variables injected into the template above)
3. Optionally, the **ProxmoxNodeClass**, **NodePool**, and **ProxmoxUnmanagedTemplate** / **ProxmoxTemplate** custom resources

---

## How the pieces fit together

```
ProxmoxNodeClass.metadataOptions.templatesRef  ──▶  karpenter-k3s-cloudinit-template (Secret)
ProxmoxNodeClass.metadataOptions.valuesRef     ──▶  karpenter-k3s-cloudinit-values   (Secret)
ProxmoxNodeClass.spec.instanceTemplateRef      ──▶  ProxmoxUnmanagedTemplate / ProxmoxTemplate
NodePool.nodeClassRef                          ──▶  ProxmoxNodeClass
```

When Karpenter provisions a new node, it clones the referenced Proxmox VM template, builds a Cloud-Init ISO from the template Secret rendered with the values Secret, and attaches it to the VM as a CD-ROM. The VM's `cloud-init` then configures the OS and joins the node to the K3s cluster.

---

## 1. The VM template

The chart does **not** build the Proxmox VM template — that is a one-time, out-of-band step (see `scripts/build-ubuntu-k3s-template.sh` provided alongside this chart, or build it manually). The template only needs to be an Ubuntu/Debian cloud image with:

- `qemu-guest-agent` installed (required for Proxmox to report the VM's IP/state)
- `containerd`, `runc`, `curl`, `nfs-common` (or your CNI/CSI dependencies)
- `boot: order=scsi0` rather than the legacy `boot: c` format — this is the format Karpenter writes when attaching the Cloud-Init CD-ROM, and a template still using the legacy `boot: c` format will fail with `boot.legacy: value does not match the regex pattern`. Both SeaBIOS and OVMF work fine with `boot: order=scsi0`; only the boot-order syntax matters here, not the BIOS type.
- **No Proxmox Cloud-Init drive** (`scsi1: <storage>:cloudinit`) needed — the `network-config` generated by Karpenter's own Cloud-Init ISO configures DHCP over IPv4 on the detected interface, which is enough for these nodes.

### K3s installation: two supported strategies

This chart supports two ways to get the K3s agent binary onto the node, controlled by `cloudInitTemplate.installK3sAgent`.

**Strategy 1 — install via Cloud-Init at provisioning time** (`installK3sAgent: true`)
The VM template does **not** contain K3s at all. The generated `user-data` downloads and installs the K3s agent on every boot, using the real server URL/token from the values Secret. Simple, but adds ~10-20s to node startup and requires outbound internet access from every node at boot time.

You can build this template by running the provided script on a Proxmox Host with `--k3s-mode none` (the script's default), so the resulting image is a plain Ubuntu cloud image with no K3s installed at all:

Example:
```bash
./scripts/build-ubuntu-k3s-template.sh \
   -c noble \
   -i 9000 \
   -n ubuntu-noble-template \
   -b vmbr1 \
   -s storage-name \
   -d 10G \
   -t

```
`-t`/`--template` converts the resulting VM into a Proxmox template once the build completes.
Set `cloudInitTemplate.installK3sAgent: true` in `values.yaml` to match.


**Strategy 2 — pre-install via VM template first-boot script** (`installK3sAgent: false`, the default and recommended approach)
The VM template installs the K3s agent **once**, at template-build time, using dummy values, and leaves the service disabled and stopped:

```bash
--firstboot-command "curl -sfL https://get.k3s.io | K3S_URL=https://dummy:6443 K3S_TOKEN=dummy INSTALL_K3S_SKIP_START=true INSTALL_K3S_SKIP_ENABLE=true sh -s - agent"
```

Two details matter here and are easy to get wrong:

- **Use `--firstboot-command`, not `--run-command`.** `virt-customize --run-command` executes while the disk image is offline being customized — it has no network access, so `apt install` and `curl` silently fail or hang. `--firstboot-command` defers execution to the VM's actual first boot, when the network is up.
- **Pass `K3S_URL` (even a dummy one).** Setting `K3S_URL` makes the K3s installer default its exec command to `agent` automatically — appending `agent` explicitly (`sh -s - agent`) is redundant once `K3S_URL` is set, though harmless. Without `K3S_URL` at all, the installer creates `k3s.service` (server mode) instead of `k3s-agent.service`.

At provisioning time, Cloud-Init overwrites `/etc/rancher/k3s/config.yaml` with the real `server`, `token`, and `kubelet-arg` values, then starts the already-installed `k3s-agent` service.

You can build this template by running the provided script on a Proxmox Host with `--k3s-mode agent` and no `--k3s-url`/`--k3s-token`, so the script installs the K3s agent with dummy join values, skips enabling/starting it, and leaves the real join configuration to Cloud-Init.

Example:
```bash
./scripts/build-ubuntu-k3s-template.sh \
   -c noble \
   -i 9000 \
   -n ubuntu-k3s-agent-template \
   -b vmbr1 \
   -s storage-name \
   -d 10G \
   -t \
   -m agent

```

> **Bootstrapping a real cluster from the same script:** the script also supports building a **K3s server** node directly, with the service started immediately — useful to stand up the very first control-plane node this chart's workers will later join. Omit `-t` to keep it as a regular bootable VM rather than a template, and pass `--k3s-start`:
>
> ```bash
> ./scripts/build-ubuntu-k3s-template.sh \
>   -c noble \
>   -i 9100 \
>   -n k3s-master-01 \
>   -b vmbr1 \
>   -s storage-name \
>   -d 20G \
>   -m server \
>   --k3s-token "$K3S_TOKEN" \
>   --k3s-start
> ```
>
> If `--k3s-token` is a secure-format token (`K10<ca-hash>::server:<password>`), only the `<password>` portion is honored by K3s when bootstrapping the very first server — see [K3s token docs](https://docs.k3s.io/cli/token). Pass a short-format token (just the password) directly if you want full control over the value, or omit `--k3s-token` entirely and let K3s generate one (retrieve it afterwards from `/var/lib/rancher/k3s/server/token` on the new server).

## 2. Cloud-Init template (`cloudInitTemplate`)

Rendered into a Secret named `cloudInitTemplate.name` (default `karpenter-k3s-cloudinit-template`), referenced by `ProxmoxNodeClass.spec.metadataOptions.templatesRef`.

### Values

| Key | Description |
|---|---|
| `cloudInitTemplate.name` | Name of the generated Secret. |
| `cloudInitTemplate.installK3sAgent` | `true`/`false` — see strategies above. Default `false`. |
| `cloudInitTemplate.k3sVersion` | K3s version to install when `installK3sAgent: true` (e.g. `v1.35.2+k3s1`). Leave empty (`""`) to install the latest stable release — the K3s installer treats an empty `INSTALL_K3S_VERSION` the same as if it were unset. |
| `cloudInitTemplate.resetMachineId` | `true`/`false` — see **Machine ID reset** below. Default `true`. |

### What the rendered `user-data` contains

- An SSH user (`sshUser`) with sudo, a password hash, and an SSH public key (all from the values Secret)
- `/etc/rancher/k3s/config.yaml` with `server`, `token`, and `kubelet-arg` (including `provider-id`, populated from `{{ .Metadata.ProviderID }}` — **do not hand-roll this from `.NodeClaim.Labels`/`.Annotations`**, the provider exposes it directly and pre-formatted)
- A `runcmd` block that either installs K3s (strategy 1) or just enables/starts the pre-installed `k3s-agent` service (strategy 2)

### Machine ID reset (`resetMachineId`)

**Why this exists:** if the Proxmox VM template was built without clearing `/etc/machine-id` (e.g. via `virt-customize --truncate /etc/machine-id`, or equivalent in whatever pipeline built it — Packer, Terraform, manual), every VM cloned from it inherits the **same** machine ID. `systemd-networkd` derives its DHCP client identifier (DUID) from the machine ID, and some DHCP servers (dnsmasq included) key leases off that identifier rather than the MAC address — so every clone ends up requesting, and receiving, the **same IP address**. Symptoms: nodes silently fail to join (wrong/colliding IP), intermittent SSH access, ARP flapping between nodes.

When `resetMachineId: true`, the generated `runcmd` clears and regenerates the machine ID on first boot:

```yaml
- rm -f /etc/machine-id /var/lib/dbus/machine-id
- systemd-machine-id-setup
- systemctl restart systemd-networkd
- until getent hosts get.k3s.io >/dev/null 2>&1; do sleep 1; done   # only when installK3sAgent: true
```

Two non-obvious details baked into this sequence:

- `systemd-machine-id-setup` does not generate a random ID — on a VM with a DMI/SMBIOS UUID available (true for any Proxmox VM), it derives the machine ID from that VM UUID instead. This is fine and sufficient, **provided each clone has a distinct Proxmox VM UUID**, which is the default behavior for a full clone.
- `systemctl restart systemd-networkd` causes a short window where DNS resolution fails (`curl` exit code `6`, `CURLE_COULDNT_RESOLVE_HOST`) immediately after the restart — a `resolv.conf` race, not a fixed delay. A blind `sleep N` is fragile; the `until getent hosts ...` loop polls until resolution actually works (in testing, around 10–15s on first boot) before downloading K3s.

**Set `resetMachineId: false` only if you have independently verified that your VM template build pipeline already truncates `/etc/machine-id` before converting the VM to a template** (e.g. `virt-customize -a <disk> --truncate /etc/machine-id`). If in doubt, leave it `true` — it is idempotent and harmless even on a template that already handles this correctly.

## 3. Cloud-Init values (`cloudInitValues`)

Rendered into a Secret named `cloudInitValues.name` (default `karpenter-k3s-cloudinit-values`), referenced by `ProxmoxNodeClass.spec.metadataOptions.valuesRef`. These are the variables substituted into the template Secret above (`.Values.*` in the Go template).

| Key | Description |
|---|---|
| `cloudInitValues.name` | Name of the generated Secret. |
| `cloudInitValues.k3sServerURL` | URL of the existing K3s server, e.g. `https://master.example.local:6443`. **The hostname must be included in the server's TLS certificate SANs** (`tls-san` in the server's `/etc/rancher/k3s/config.yaml`) — otherwise nodes fail to join with `x509: certificate is valid for ... not <your-hostname>`. After adding a `tls-san` entry to an existing server, run `k3s certificate rotate` and restart `k3s` for it to take effect. |
| `cloudInitValues.k3sToken` | K3s server token (`/var/lib/rancher/k3s/server/node-token` on an existing server node). Treat as a secret — avoid committing it in plaintext to version control. |
| `cloudInitValues.sshUser` | Username created on each worker node. |
| `cloudInitValues.sshKey` | (Optional) SSH public key for `sshUser`. |
| `cloudInitValues.sshPasswordHash` | (Optional) Password hash for `sshUser`, generated with `openssl passwd -6 "password"`. Useful for out-of-band console/VNC access when SSH/network debugging is needed. |

> **Note on node naming:** do **not** set `with-node-id: true` in the K3s config. Karpenter matches a `NodeClaim` to its Kubernetes `Node` by name; `with-node-id` appends a random suffix to the node's hostname-derived name, breaking that match and leaving the `NodeClaim` permanently in `Ready: Unknown` with `Reason: NodeNotFound`. Omit it entirely — K3s then uses the Cloud-Init `meta-data` hostname as-is, which matches what Karpenter expects.

## 4. Karpenter Custom Resources (optional)

The chart can optionally create the `ProxmoxNodeClass`, `NodePool`, and `ProxmoxUnmanagedTemplate`/`ProxmoxTemplate` resources, so the whole node pool can be deployed as a single Helm release.

### `nodeTemplate`

One entry per VM template you want Karpenter to be aware of.

| Key | Description |
|---|---|
| `nodeTemplate.<name>.enabled` | Create this `ProxmoxUnmanagedTemplate`/`ProxmoxTemplate` resource. |
| `nodeTemplate.<name>.kind` | `ProxmoxUnmanagedTemplate` (template not managed by Karpenter, e.g. built by an external script as described above) or `ProxmoxTemplate` (Karpenter manages the template lifecycle itself). |
| `nodeTemplate.<name>.spec` | Raw spec, e.g. `templateName: <proxmox-template-name>`. See the [nodetemplateclass reference](https://github.com/sergelogvinov/karpenter-provider-proxmox/blob/main/docs/nodetemplateclass.md). |
| `nodeTemplate.<name>.tags` | (Optional) Match the template by Proxmox tags instead of/in addition to name. |

### `nodeClass`

One entry per `ProxmoxNodeClass`. Ties together the VM template, the boot disk sizing, and the two Cloud-Init Secrets above.

| Key | Description |
|---|---|
| `nodeClass.<name>.enabled` | Create this `ProxmoxNodeClass`. |
| `nodeClass.<name>.spec.instanceTemplateRef` | Points at the `nodeTemplate` entry above. |
| `nodeClass.<name>.spec.bootDevice` | Root disk size and Proxmox storage. |
| `nodeClass.<name>.spec.metadataOptions` | Wires up `templatesRef`/`valuesRef` to the two Secrets generated by this chart, and sets `type: cdrom` so Cloud-Init is delivered as an ISO. |
| `nodeClass.<name>.spec.tags` | (Optional) Tags applied to provisioned VMs in the Proxmox UI, for visibility. |

See the [nodeclass reference](https://github.com/sergelogvinov/karpenter-provider-proxmox/blob/main/docs/nodeclass.md) for the full spec.

### `nodePools`

One entry per Karpenter `NodePool`. Standard Karpenter NodePool spec — see [karpenter.sh/docs/concepts/nodepools](https://karpenter.sh/docs/concepts/nodepools). `limits` caps the aggregate CPU/memory this pool is allowed to provision; `requirements` constrain instance selection (architecture, instance type, capacity type, etc.).

## Troubleshooting checklist

If a node is created in Proxmox but never reaches `Ready` in Kubernetes, work through these in order — each corresponds to a real failure mode encountered while building this chart:

1. **`NodeClaim` stuck at `Ready: Unknown`, event `Nodeclaim does not have an associated node`**
   Check `kubectl get node <name> -o jsonpath='{.spec.providerID}'`. It must exactly match the NodeClaim's `Provider Id` (`proxmox://<region>/<vmid>`). If it shows `k3s://<hostname>` instead, the `provider-id` kubelet-arg isn't being applied — confirm the rendered `config.yaml` (mount the Cloud-Init ISO: device name varies by template (`/dev/sr0` or `/dev/cdrom` are both common — check with `lsblk | grep rom` first), then `mount -o ro /dev/sr0 /mnt && cat /mnt/user-data`) actually contains it.

2. **Node never appears in `kubectl get nodes` at all**
   SSH/console into the VM and check, in order: `which k3s` (installed?), `systemctl list-unit-files | grep k3s` (which service exists — `k3s` or `k3s-agent`?), `cat /etc/rancher/k3s/config.yaml` (did Cloud-Init write it?), `journalctl -u k3s-agent -n 50` (why did it fail to start?).

3. **`journalctl` shows `x509: certificate is valid for ... not <hostname>`**
   The K3s server's TLS certificate doesn't include the hostname used in `k3sServerURL`. Add it to `tls-san` on the server and run `k3s certificate rotate`.

4. **`journalctl` shows `failed to bootstrap cluster data: etcd disabled`**
   The node started `k3s.service` (server mode) instead of `k3s-agent.service` (agent mode). Check which unit file exists — this happens when the template's first-boot install script omitted `K3S_URL`/`agent`, or when Cloud-Init's `runcmd` references the wrong unit name.

5. **Every new node gets the same IP address**
   Check `cat /etc/machine-id` on two different nodes. If identical, `resetMachineId` is either disabled or not taking effect — see the Machine ID section above.

6. **`curl: (6) Couldn't resolve host` right after a `systemd-networkd` restart**
   DNS race after the network restart. Confirm the `until getent hosts ...` line is present in the rendered `runcmd` (this is automatic when `resetMachineId: true`).

7. **`NodeClaim` is destroyed after ~15 minutes while you're mid-debug**
   This is Karpenter's `registration_timeout` — expected behavior in production, inconvenient while iterating. Scale Karpenter to zero replicas while debugging (`kubectl scale deploy -n kube-system <karpenter-deployment> --replicas=0`), or test against a manually cloned VM outside of Karpenter's lifecycle entirely.

8. **`failed to attach cloud-init ISO ...: boot.legacy: value does not match the regex pattern`**
   The VM template uses legacy boot-order syntax `boot: c` instead of `boot: order=scsi0`.

9. **Template build fails with `apt-get`/`curl` errors inside `virt-customize`**
   If using `--install` or `--run-command`, the customization step has no network access on some hosts/backends. Switch to `--firstboot-command` for anything requiring internet access (package installs, K3s download) — it runs on the VM's actual first boot instead of during offline image customization.
